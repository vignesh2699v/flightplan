Flightplan

Reads a project, tests the premise, files one plan, then hands over one ticket at a time with its skills attached — and tracks what actually happened.

Supersedes rebuild-prompt v1.16 Decisions settled 20 Executes work never

The contract

Unchanged, and it is the line everything else hangs off: it never executes the work. It reads, plans, routes, and hands over prompts. What changes is that the plan now lives on a page instead of in a message, and the page learns what happened.

The tracker gets its data without breaking that. Each ticket's prompt ends by telling the receiving session to write its own result back to the page — so the record updates itself, and you never become the messenger.

Pipeline

1

Read

Memory, git log, README, package.json, existing files. Infer rather than ask — the v1.1 lesson, after a six-question interview round got interrupted, was never “don't gather context”. It was “don't ask what you could look up.”

2

Grill

After reading, not before — so it challenges the premise against what the project actually contains. Four questions maximum, gaps only. Zero when reading covered everything.

3

File the plan

Publish one artifact: context, outcome, approach, ticket list. This is the only thing read end to end, and it is read once.

4

Ballot

One round at approval, capped at the four most consequential contested picks. Every other ticket states its pick and runner-up inline, to override in chat.

5

Serve one ticket

The full prompt is written just-in-time, against what actually happened in the tickets before it. Nothing goes stale waiting its turn.

6

Write back

The ticket's prompt instructs the session to update the tracker: status, one line of outcome, a link to the evidence. Then the next ticket is written.

Anatomy of the page

Context — approve once
What this is — README, line 3 Who it's for — CLAUDE.md What exists now — git log, 40 commits What success looks like — you, at grilling What's out of scope — you, at grilling

Every field shows where it came from. Since inference does the work, the source trail is how a wrong inference gets caught in two seconds instead of three tickets later. The last two fields are the ones reading rarely settles — when grilling has questions to spend, they go here first.

Tickets — one verifiable outcome each

Title, capability and done-criterion at approval. The full prompt arrives when the ticket goes live. Typically 8–15 for a real project.

Tracker — the only live part
T-01 Done Audit found 6 friction points, 2 structural → screenshots
T-02 Done Redesign covers 5 of 6; one deferred with reason → artifact
T-03 Live Implement the new step order
T-04 Pending Write tests for the new flow

Each finished row also carries a quiet “safe to hand off here” marker — always true at a ticket boundary, always there when wanted, never interrupting when not.

Name/flightplan

Deleted

Segments — but each boundary for a different reason

Model boundary existed because a directly-run task inherits the session model, so a tag only binds where the prompt physically stops. One ticket per paste stops every time. Gone. Finding boundary existed because a long prompt goes stale before it finishes — just-in-time prompts remove the staleness rather than the stop. Gone. Approval boundary is not free: one verifiable outcome per ticket does not guarantee a destructive or outward-facing step is isolated rather than sitting mid-ticket. That guard survives as a rule — anything irreversible gets its own ticket, and that ticket says so.

The three output tiers

Single-shot, Compact and Full are replaced by two paths: initialise a session, or answer a small ask in one routed line.

The compaction checkpoint as a chat line

Survives only as a marker on the tracker. Once state lives on the page rather than in the transcript, compaction stops being something to defend against.

Open risks

The tier system didn't actually die

Three tiers were voted out, then a one-liner survived for cold small asks and mid-session asks became tickets. That is still two paths with a routing decision between them. Design it deliberately, or it reappears as an accident.

Twelve tickets is twelve round trips

One verifiable outcome per ticket means a real project is twelve pastes, twelve returns, twelve writebacks. That is the number, and it is the most likely reason this gets abandoned in week two. Measure it on the first real project rather than assuming.

Migration

  • Same repository, same release history, same eval harness. Fixtures are rewritten; the v1.16 set stays alongside as the baseline.
  • Skill directory and command become flightplan; a v2.0 release explains the rename.
  • Anyone on the old install keeps a working copy — it simply stops receiving changes.
  • ~/.claude/rebuild-prompt/history.md carries over unchanged: task shape and capability names only, never prompt content.

Decided without asking

Detail rather than direction — listed so nothing is silently assumed:

  • Ticket IDs run T-01 upward, stable for the job's life.
  • Each ticket prompt carries the artifact's file path and URL, since the receiving session needs both to write back.
  • Model and effort tags stay, per ticket.
  • The last ticket's writeback closes the plan rather than offering another handoff.
  • One page per project, keyed by slug, recovered through the Artifact list action.
