# v1.13 vs v1.12 — did the release beat the version it replaced?

v1.13 shipped on direct feedback (scan fatigue, cost defaults, drift, closing
the loop) with no fixture run behind it — the fixture set existed
(`fixtures.md`, from the v1.12 measurement) but wasn't used before release.
This is that comparison, run after the fact: same 10 fixtures, same
non-interactive dispatch protocol, this time comparing v1.13's pipeline
against v1.12's instead of skill-vs-baseline.

## Method

Deviates from `fixtures.md`'s literal "baseline vs skill" protocol in one
way: both conditions are the skill, at two different versions, since the
question isn't "does the skill beat a plain answer" (already measured) but
"did this release improve the skill." For each fixture, two fresh
general-purpose agents were dispatched — one given the exact v1.12
`SKILL.md`+`routing-guide.md` text (frozen via `git show v1.12:...`), one
given the exact v1.13 text (current) — both told to follow the pipeline
faithfully, auto-select "(Recommended)" wherever `AskUserQuestion` would
fire, and return only the final delivered output. 20 generations total.

Two fresh-context judges then scored 5 fixture pairs each, blind — outputs
labeled "Output A" / "Output B" with no version markers, order varied per
fixture. Judges scored: routing/approach accuracy, completeness (success
criteria, constraints, scope guards), structural soundness (model/effort
tagging, segmentation), and — new for this run — fit to the job's actual
size, since that's what v1.13 specifically targeted.

**A mistake worth stating plainly:** while assembling the two judge prompts,
the intended alternating A/B pattern wasn't actually followed — outputs were
pasted in generation order in places, not alternated. Un-blinding was done
by matching each judge's "Output A" / "Output B" text against the known
generation content line-by-line, not by trusting the intended scheme. The
numbers below are checked against actual text, but this is a process gap:
a labeling script instead of hand-pasting would remove this failure mode
for the next run.

## Result

| # | Fixture | Winner | Margin |
|---|---|---|---|
| F1 | Spinner (trivial, single-task) | v1.13 | clear |
| F2 | Premium landing page | v1.13 | mild |
| F3 | 3 uncontested tasks | v1.12 | mild |
| F4 | Refactor + security review | v1.13 | mild |
| F5 | 5-task onboarding (segments) | v1.12 | clear |
| F6 | BEM rename + architecture review | v1.12 | mild |
| F7 | "Make the app faster" | v1.13 | clear |
| F8 | "Help me fix the bug" | v1.12 | mild-to-clear |
| F9 | Verify signup flow | v1.12 | mild |
| F10 | GraphQL migration plan | v1.12 | mild-to-clear |

**v1.12 won 6, v1.13 won 4.** This release did not clearly beat the version
it replaced. That's a real result, not a rounding-down — see below for why,
and it isn't the same failure mode across all six v1.12 wins.

## Where v1.13 won, and why it's real

**F1 and F7 are the clean wins, and they're exactly what the release was
built for.** F1 (a one-file spinner fix): v1.12 tagged it `claude-opus-5 |
xhigh` — the ceiling — while its own routing note said the task was "not a
UI craft problem." v1.13 reached the same routing conclusion but tagged it
`claude-sonnet-5 | high`, one rung up from baseline instead of maxed out.
F7 ("make the app faster"): v1.12 wrapped a single diagnosis-only task in a
model-plan table plus a self-invocation boilerplate line pointing at no
named skill; v1.13 delivered the same diagnosis-only scoping in one
compact block. Both are the over-resourcing and over-templating problems
v1.13 set out to fix, fixed.

**F4 is a wash that reads as a v1.13 win for the wrong reason.** v1.12's
security-review task dispatched "the ecc:security-reviewer agent" — a name
that matches neither the actual installed skill (`ecc:security-review`) nor
the plain-name convention every other subagent in the set uses. v1.13 used
the real skill name. This is a capability-naming defect in v1.12's output,
not evidence v1.13's routing logic is better — worth knowing, not worth
claiming as a design win.

## Where v1.12 won, and the pattern behind four of the six

**F6, F8, F9, and F10 share one root cause: the Compact and Single-shot
tiers have no slot for constraints, and nothing prompts for one.** The Full
tier template has a `<constraints>` block built into its structure — Compact
and Single-shot don't. The result, concretely:

- **F6** (BEM rename + read-only architecture review): v1.12's output
  stated the review step is read-only, since state-management code is being
  inspected, not touched. v1.13's Compact-tier output dropped that guard
  entirely.
- **F9** (verify a signup flow before marketing promotes it): v1.12
  constrained the verification to test/sandbox accounts, never real
  customer data, and explicitly kept "is this ready to promote" out of the
  agent's hands. v1.13's shorter output had neither.
- **F10** (a migration plan real engineers will execute against): v1.12
  stacked a second, domain-specific skill (`/ecc:api-design`) onto the
  planning task and explained two rejected alternatives with reasoning.
  v1.13's Compact tier has no "why these skills" table, so that routing
  justification simply isn't there to give.

This is the tradeoff the tier system makes structural, not incidental: Full
tier's ceremony wasn't only decorative overhead — some of it was carrying
constraints and routing justification that a trivial task doesn't need but
a real one does, and the tier boundary in `SKILL.md` § 1 (2–3 tasks → Compact,
regardless of what's at stake in those tasks) doesn't distinguish the two.

**F8 is a different, second defect: the effort-escalation trigger over-fires
on ambiguity that isn't expensive to resolve.** "Help me fix the bug," zero
signal. Both versions correctly refuse to guess and narrow to a
clarifying question. v1.12 tagged that at `sonnet-5 | low` — cheap, because
asking a question is cheap. v1.13's routing-guide.md escalation rule fires
on "a spec still genuinely ambiguous after grilling" — and this fixture's
spec is about as ambiguous as it gets — so it tagged the same
one-clarifying-question task at `opus-5 | high`. The rule is reading
"ambiguous" as "expensive," but a task that's just a question isn't
expensive regardless of how ambiguous the underlying bug is. The escalation
trigger needs to key off what the *task itself* costs to get wrong, not
whether the *premise* was ambiguous.

**F5 is genuine disagreement about the skill's own segment rule, not a clear
defect either way.** v1.12 wrote out all 5 tasks in a 3-segment delivery;
v1.13 delivered only the audit and marked the other 4 tasks provisional,
citing a finding boundary. The judge scored this as v1.13 under-delivering,
since nothing in tasks 2-5 actually required the audit's findings to write
generic instructions. But `README.md` § Design notes states the segment
rule exists precisely because "a long prompt goes stale before it's
finished" when later tasks depend on findings that haven't happened yet —
and this fixture's own shape (`fixtures.md` names it "should segment at a
finding boundary") says punting here is correct, not a shortfall. Whether
v1.13's choice was right depends on which principle you weight — plan
completeness now, or avoiding stale instructions later — and that's a real
tension in the skill's own design, not something this fixture resolves.

## Two fixes this run earned

1. **Give Compact and Single-shot a constraints slot.** Not the full
   `<constraints>` block unconditionally — that would re-inflate exactly
   what the tiers exist to trim — but a rule that a hard constraint,
   destructive-action guard, or credential boundary is never dropped by
   tier, only the ceremony around it is. F6 and F9 both had a real
   constraint to state; the template gave neither tier a place to put it.
2. **Rework the escalation trigger so ambiguity and cost are separate
   checks.** F8 shows "spec is ambiguous" and "task is expensive" can point
   in opposite directions on the same task. The trigger should ask what the
   task itself costs to get wrong, not treat post-grilling ambiguity as a
   proxy for cost.

## What this run didn't cover

- Same single-run-per-fixture limitation as the v1.11 comparison — no
  variance check, and a different agent instance on either version could
  move any of the "mild" results.
- The A/B assembly mistake (above) means this run's rigor is weaker than
  the v1.11 comparison's; the correctness of the unblinding rests on manual
  text-matching, not a labeling process that couldn't have been mixed up
  to begin with.
- Doesn't test the carry-forward behavior (continuing a job across turns)
  or the closing-checklist mechanism at all — no fixture in the set spans
  two `/rebuild-prompt` invocations in one session.
