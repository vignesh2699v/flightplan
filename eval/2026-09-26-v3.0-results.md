# v3.0 vs v2.1 — the first measurement of the plan-and-ticket contract

v2.0 and v2.1 shipped without a fixture run: the v2 design spec promised
rewritten fixtures, and they were never written. This run writes them
(`fixtures-v3.md`, built on a real fixture project from `build-fixture.sh`)
and compares v3.0 with the exact v2.1 text on five cases: four first
invocations and one record-and-serve step.

## Method

Each fixture ran once per version, in a fresh general-purpose subagent with
its own clone of the fixture project and its own stand-in home directory.
Both versions got word-for-word the same instructions apart from the skill
path (`fixtures-v3.md` § Running a pair). Token use, tool calls and
wall-clock time come from each subagent's completion notice.

Grading was blind. Before any grader ran, a script copied each pair into
folders labelled X and Y, scrubbed anything that named a version (skill
paths, the old `rebuild-prompt` folder, URL suffixes), and wrote the label
map to a file. The first random draw mapped v3 to X in all four cases; it
was replaced with a balanced draw before grading, and the file records
that. Each grader graded both runs against assertions fixed before it saw
any output, then picked a winner. A separate judge read screenshots of the
two plan pages as a non-technical shop owner would.

v3 was not frozen during the run: the first round measured the v3 text as
first drafted, the evaluation's findings were fixed between rounds, and the
two cases whose fixes needed proof were rerun (§ After the fixes).

## Results

| Case | Winner | v3 assertions | v2.1 assertions | v3 tokens | v2.1 tokens | v3 time | v2.1 time |
|---|---|---|---|---|---|---|---|
| P1 small ask, payments code | **v3**, clear | 5/5 | 4/5 | 99.6k | 121.5k | 380s | 463s |
| P2 full plan, deploy last | **v3**, mild | 11/11 | 9/11 | 200.9k | 233.7k | 969s | 1235s |
| P3 two very different models | **v3**, clear | 7/7 | 6/7 | 216.2k | 239.7k | 986s | 1245s |
| P4 no target ("fix the bug"), first draft | v2.1, clear | 3/4 | 4/4 | 91.6k | 95.8k | 264s | 256s |
| P4 after the fix | **v3**, mild | 4/4 | 4/4 | 89.1k | 95.8k | 229s | 256s |
| P5 record T-01, serve T-02 | **v3**, mild | 8/9 | 6/9 | 143.3k | 189.6k | 659s | 920s |

Counting P4 after its fix, v3 won all five cases, passed 35 of 36
assertions against v2.1's 29, and used **15% fewer tokens** (749k against
880k) and **22% less time** (54 minutes against 69).

The non-technical judge scored the two plan pages after P5 at **30 of 30
for v3 and 16 of 30 for v2.1**, and would clearly rather be sent v3's: "Y
is written for me as the shop owner; X is written for a programmer." On
v2.1's page each step's purpose and the audit's result sat behind an arrow
or an Outcome button; on v3's, every step says what it is for and the
finished audit shows its result on its card.

## Where the page and the prompts earned it

- **P5 is the step users repeat most, and v3 made it one turn.** v3's run
  recorded T-01 and served T-02 in one 80-word message; v2.1 needed the user
  to send `/flightplan` and then answer a re-plan question, three messages
  and about 560 words before T-02 went live. v3 read 39 of the page's 560
  lines — the data block — where v2.1 re-read and hand-edited its HTML.
- **Model tags.** v2.1 put effort levels on two Haiku tickets, which Haiku
  doesn't support, and its P3 plan switched model four times, resetting the
  prompt cache each time. v3 switched once, and its live prompts suited the
  model they were tagged for.
- **Small asks read one file.** v3's P1 run read only SKILL.md. v2.1 read the
  284-line reference file to reach a one-line template, and its prompt asked
  for an end-to-end check the repository couldn't run.

## Where v2.1 was better, and what changed because of it

The graders were specific about v2.1's strengths, and each became a fix:

- **P4, first draft.** v2.1 offered three real candidate bugs it found by
  reading; v3 asked an open question because its rule said never to guess.
  The rule now says to offer what a quick read turns up, and the rerun won.
- **P2 engineering.** v2.1 noticed the users API had no storage behind it
  and planned a test harness before the build, and it deployed through the
  README's own script. Planning now checks tickets against what the code can
  do today, and routing puts the project's documented route ahead of an
  installed tool that does the same job.
- **P3 reading.** v2.1 found that nothing imports the store, while v3
  repeated the store's own comment as fact and miscounted checkout's
  classes. Reading now treats comments and docs as leads to confirm.
- **P5 honesty.** v2.1 judged T-01 clause by clause and called it a fail;
  v3 called it a pass while its own result sentence named the gaps. Recording
  now calls a pass only when every part is met, and offers one choice —
  carry the gap forward or retry — when the next ticket could absorb it.

## After the fixes

- **P4 rerun:** the fixed v3 offered the same three verified candidates as
  v2.1 in fewer words, and a fresh blind grader preferred it (mild).
- **P5 rerun, with the rule that a pass needs every part met:** the
  session judged T-01 part by part and called it a fail, and it corrected the
  audit's own claim to have walked the flow with a test account, which no one
  could have done because nothing mounts the flow yet. It offered one choice,
  carry the gaps into T-02 (recommended) or retry, took the default, recorded
  T-01 done with the gaps named, widened T-02's done-criterion to cover them,
  and served T-02. It used 146k tokens, 24 tool calls and 649 seconds, and read
  37 of the page's 560 lines. The first P5 runs were told to treat T-01 as
  complete and correct; this rerun wasn't, so it shows the rule's behaviour
  rather than a controlled comparison.

The other fixes (plan realism, documented routes, confirming comments, the
plan page's "Up next" and technical-notes changes) came from graders' reasons
and were checked by the linters and a rendered test page, not by a rerun.

## Skill text loaded

| Path | v2.1 words | v3 words | |
|---|---|---|---|
| Small ask | 3,070 | 1,726 | −44% |
| Full plan, first run | 3,070 | 3,972 | +29% |
| Record and serve next | 3,070 | 3,440 | +12% |

The planning and recording paths load more skill text than v2.1 did. The
first draft of v3 loaded less; the evaluation's fixes added the words back,
because each closed a failure a grader found. Whole runs still cost less,
because the skill text is a small share of a run: v2.1 wrote each plan page's
HTML from scratch (34–46 KB per page) and re-read it to edit it, while v3
copies a template and appends one-line records.

## What this run doesn't establish

- **One run per fixture per version.** No variance check; the mild margins
  could move.
- **No subagents in the runs.** The executors couldn't spawn subagents, so
  v3's routing of small, self-contained tickets to a Haiku subagent was never
  exercised; both versions kept every ticket in-session.
- **No real Artifact publishing.** Every run wrote the page locally and
  treated it as published, so recovery through the Artifact tool's list
  action is unmeasured.
- **Screenshot leak in two cases.** The screenshots given to the P2 and P3
  graders were rendered before scrubbing, so v2.1's page showed a file path
  naming its folder. The P2 grader noticed a mismatch. Treat those two
  verdicts as possibly unblinded; P5 and the page judge used screenshots
  rendered from the scrubbed files.
- **The standard for prompt fit is the one v3 was built on.** Graders judged
  "suits its model" against Anthropic's per-model guidance, which v3 follows
  and v2.1 predates. That is the requirement this release was asked to meet,
  but it favours v3 by construction on those assertions.
- **The description's triggering wasn't optimized.** The skill-creator's
  trigger loop runs `claude -p` many times, and in the cloud session this ran
  in, each child process inherited the session's identity. The command to run
  it locally is in the CHANGELOG entry.
- **Every run used the same model.** The executors ran on the session's
  model; nothing here measures a Sonnet or Haiku session running the skill.
