# v1.15 vs v1.14 — does the job page earn its place?

v1.15 moved Full-tier delivery out of chat and onto a published page: plan on
top to read, prompt below in a copy block to run, redeployed to one URL as
the job moves. This run asks two things — does the tier guardrail hold (do
Compact and Single-shot correctly stay in chat), and where the page does
fire, is the result better than v1.14's chat delivery.

## Method, and one deliberate limitation

**A 6-fixture subset, not the full 10** (`fixtures.md` F1, F3, F5, F6, F9,
F10), chosen to span the tier boundary — two that must not publish, four
that must. Session cost was the reason; the limitations it creates are in
the last section.

12 generations: each fixture run twice, once against the exact v1.14 skill
text (`git show v1.14:...`) and once against v1.15, both told to follow the
pipeline faithfully, auto-select "(Recommended)" wherever `AskUserQuestion`
would fire, and describe rather than perform any Artifact publish.

**The labeling fix worked.** Against the process gap `2026-08-09-v1.13-results.md`
records, this run wrote the A/B map to a file *before* any generation ran,
alternating per fixture. The judge's independent reconstruction of which
outputs shared a delivery mechanism matched that file exactly on every pair.
Cheap fix, worth keeping.

Judging: the tier guardrail is directly observable, so it was read off the
generations rather than judged. **Three** of the four Full-tier pairs — F5,
F6, F10 — went to one blind judge scoring routing accuracy, completeness,
structural soundness, and reviewability, explicitly told to weigh whether the
organisation helps or is ceremony rather than reward novelty. F9's pair was
generated and guardrail-checked but not judged, to hold cost down; it is
neither a win nor a loss below, and its outputs are the least examined thing
in this run.

## Result 1 — the tier guardrail holds

| # | Tier | v1.15 behaviour | Correct |
|---|---|---|---|
| F1 | Single-shot | One fenced block, no publish | yes |
| F3 | Compact | Chat, stating "classified Compact… no job-artifact page to publish" | yes |
| F5 | Full | Published `jobs/onboarding-flow-audit-redesign.html` | yes |
| F6 | Full | Published `jobs/bem-rename-tenancy-review.html` | yes |
| F9 | Full (see below) | Published `jobs/signup-flow-e2e-check.html` | yes |
| F10 | Full | Published the job page **and** routed the plan-shaped task to its own separate URL | yes |

No leakage in either direction. F10 also confirms the distinction added in
v1.15 between the job's own page and a task whose *deliverable* is a
plan — the two artifacts stayed separate, which was the specific collision
risk flagged when the section was written.

One classification worth flagging: `fixtures.md` defines F9 as a
"verification-shaped **single** task", and the v1.13 run treated it that way.
Both versions here decomposed it into four, which is what put it in Full tier
and made publishing correct. The guardrail verdict above is therefore
conditional on a decomposition the fixture's own description doesn't predict
— worth re-checking rather than trusting.

## Result 2 — the page wins 2 of 3, and loses for a reason worth acting on

| Pair | Fixture | Winner | Margin |
|---|---|---|---|
| 1 | F5 — onboarding audit chain | **v1.15** | mild |
| 2 | F6 — BEM rename + tenancy review | v1.14 | mild |
| 3 | F10 — REST → GraphQL | **v1.15** | clear |

**Where it won, the page was load-bearing.** F5 and F10 are both genuinely
multi-session, finding-gated jobs. On F10 the judge called the margin clear:
v1.15 put a falsifiable constraint on the pivotal decision ("a recommendation
to proceed counts only if the cheapest non-GraphQL alternatives were rejected
in writing"), escalated the right task and explicitly declined to escalate
the other while citing the rule that forbids it — the v1.14 fix working as
intended — and reported grilling's empty result honestly rather than
inventing findings.

**Where it lost, the page was scaffolding.** The two versions decomposed F6
differently, and that is the whole result. v1.14 produced five tasks across
two segments, split at a model boundary, and delivered two blocks with a
concrete "stop here, switch this session, paste the next block". v1.15
produced four tasks in **one** segment — reaching Full tier on task count
alone — and still built header, plan, segments and a status table in which
nothing had status, around a delivery its own header called one session. The
judge's phrasing: a page nobody will return to is overhead.

## The finding this run earned

**The publish trigger needs both conditions, not either one.** Its history is
now three positions across two rounds of pure reasoning and one of
measurement:

- v1.15 first draft keyed it to Full tier.
- A review round narrowed it to multi-segment on efficiency grounds — a
  4-task single-segment job pays for a page it never redeploys.
- A later round reversed that, arguing the review surface tracks how much a
  job has to say, which is what tier measures, and that gating on segments
  would send the heaviest single-segment job to chat.

Both arguments are sound and this run shows both are incomplete. The page's
value is the product of the two, not either alone: it needs a job big enough
that the plan and prompt shouldn't share a surface **and** a job that will
actually be returned to. v1.15's F6 had the first — four tasks, comfortably
Full — and not the second, since it resolved to a single segment, and the
scaffolding cost it a pair it might otherwise have won.

Recommended: publish when the job is Full tier *and* spans more than one
segment; deliver a single-segment Full job in chat with the "why these
skills" table and model plan below the block, as v1.14 did. Under that rule
v1.15's F6 delivers in chat, which is the outcome this run says it should
have had.

## The second finding: two of the page's wins aren't the page

The judge isolated the highest-value-per-line content in the whole set as
**"What grilling ruled out"** and the **per-task escalation reason** — both
introduced in v1.15's page structure, both entirely separable from where
delivery happens. They are what let a reviewer confirm the job was understood
without reading the prompt block, which is the whole reviewability claim.
Neither needs a page. Both should appear in Compact deliveries too.

## The regression this run found

**v1.15's page dropped operational constraints v1.14 carried.** F6 is a
codebase-wide rename, and v1.14's delivery constrained it to a clean branch,
flagged externally-reachable selectors (test hooks, analytics, third-party
integrations) as not-to-be-renamed, limited the change to the listed 40, and
required reviewable commit slices. v1.15's page carried none of them — its
only job-level constraint was the tenancy ambiguity. The judge named this as
what won the pair outright.

This is the same defect class the v1.14 release fixed for Compact and
Single-shot, reappearing one tier up: the page's per-task constraint slot
exists, but nothing drives job-level operational guards into it the way the
Full tier `<constraints>` block did.

## What this run didn't cover

- Four of ten fixtures untested against v1.15 (F2, F4, F7, F8), so this is
  not comparable to the v1.13 run's coverage.
- One run per fixture per version — no variance check, and both "mild"
  margins could move.
- Nothing tested the page being *read back* on resume, which is the
  mechanism v1.15 claims makes a job survive a compaction. Every fixture is
  a first invocation. That claim remains unmeasured.
- No fixture exercised the Artifact `list` recovery path or its miss branch.
