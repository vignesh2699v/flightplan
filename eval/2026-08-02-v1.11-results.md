# Baseline vs. skill — first comparison, run against v1.11

Ten releases (v1.0–v1.11) shipped on reasoning alone — every changelog entry
argues why a change should help, none measures whether it did. This is the
first run that actually compares `rebuild-prompt`'s output against a plain
"just help me" baseline, on the fixtures in `fixtures.md`, scored by judges
with no knowledge of which output came from which condition.

## Method

10 fixtures × 2 conditions (baseline, skill) = 20 generations, each a fresh
subagent dispatch. Two fresh-context judges then scored 5 fixture pairs each,
blind — labels "Output A" / "Output B" randomized per fixture, un-blinded
only after scoring. Full fixture text and dispatch instructions: `fixtures.md`.

## Result

| # | Fixture | Winner | Margin |
|---|---|---|---|
| F1 | Spinner (trivial, single-task) | Baseline | clear |
| F2 | Premium landing page | Skill | clear |
| F3 | 3 uncontested tasks | Skill | mild |
| F4 | Refactor + security review | Skill | clear |
| F5 | 5-task onboarding (segments) | Skill | clear |
| F6 | Two-model CSS+arch job | Toss-up | — |
| F7 | "Make the app faster" | Baseline | clear |
| F8 | "Help me fix the bug" | Baseline | clear, and flags a real bug (below) |
| F9 | Verify signup flow | Skill | mild |
| F10 | GraphQL migration plan | Baseline | clear |

**Skill preferred in 5, baseline in 4, toss-up in 1.** Not the clean win ten
changelog entries of pure reasoning would suggest. That's the point of
running this — a real comparison surfaces what confident-sounding release
notes don't.

## Where the skill earns its keep

**F5** is the clearest case. The baseline produced a full five-stage plan —
including a "redesign direction" — for a request that's explicitly
"redesign *based on what you find*." That redesign can't be written yet; it
depends on an audit that hasn't happened. The skill recognized the
dependency and delivered only the audit task, deferring the rest as
provisional. Producing a redesign before the audit exists is close to
make-believe work product; refusing to do that is the more trustworthy
behavior.

**F4** (payment code) and **F2** (subjective "premium" claim) both won on
the same mechanism: the skill's mandatory constraints and verification gate
caught something the baseline's plan left implicit or absent entirely — a
"don't ship without human go/no-go" guard on payment code, and a
screenshots-at-every-breakpoint requirement instead of accepting "looks
good" for a claim ("premium") that's notoriously easy to assert and hard to
verify.

## Where baseline won, and the confound behind it

**F1, F7, F8, F10 lost for the same underlying reason.** The skill's
contract is: return a prompt for someone (or some future session) to run —
never execute the task itself. On a small, single-shot, already-obvious ask,
a prepared prompt is a worse deliverable than a direct answer, because
answering *is* the deliverable there. Judges scored what was handed to them
— a rebuilt prompt artifact vs. a direct answer — not the outcome of
actually running that prompt. That's a confound in how this evaluation was
built, not a discovery that the skill's routing or segmentation logic is
wrong. It should have been flagged before running the eval, not after; noted
in `fixtures.md` now so future runs go in with eyes open.

**This was raised explicitly and the decision was to leave the contract
as-is.** The skill's whole premise is preparing prompts for other
sessions/models — that's the product, not an accident. Trivial single-shot
asks losing this specific comparison is an accepted, known tradeoff, not a
bug to chase.

## The one finding that isn't confounded

**F8 ("help me fix the bug," zero information given).** Baseline asked what
the bug was. The skill's inline-grilling fallback instead authorized an
**xhigh-effort speculative search** — "search logs/tests/recent diffs for
the most likely candidate and treat that as the bug." That's the opposite of
what grilling exists to prevent: guessing at scale instead of asking. Unlike
the artifact-vs-answer confound above, this isn't a category mismatch — it's
a real process defect, independent of whether the output is a prompt or a
direct answer.

**Fixed in the same pass** (SKILL.md § 0): when grilling turns up zero real
signal — no target, symptom, or file named at all — the skill no longer
defaults to a broad speculative search. It narrows the first task to
diagnosis only and marks the missing target as the `[?]` gap itself, rather
than picking a plausible-looking target and committing full effort to
chasing it.

## What this run didn't cover

- Only one run per fixture per condition — no variance check across repeated
  runs of the same fixture.
- Judges scored the delivered text, not the outcome of a human actually
  pasting the rebuilt prompt into a fresh session and running it end to end
  — the real test of the skill's value proposition, and the fix for the
  confound above.
- 10 fixtures is a first pass, not full coverage — no fixture yet tests the
  no-candidate path, the auth-gated-MCP flag, or a genuinely 2-model job
  where the *wrong* model would visibly fail the task (F6 tested a
  plausible split, not a load-bearing one).

Next run should hold the fixture set fixed (`fixtures.md`) and compare
against whatever the skill looks like after its next substantive change —
that's the actual signal this harness is for.
